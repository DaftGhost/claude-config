# Markdown 文档规范

本规则适用于仓库中的所有 Markdown 文档。文档应帮助读者快速理解背景、结论、行动项和验证方式，避免只记录零散实现细节。

## 基本规范

- 一个文档只使用一个一级标题（`#`），标题层级按顺序递进，不跳级。
- 文档开头应说明文档目的和适用范围；读者需要先知道为什么阅读文档，再阅读具体内容。
- 使用短段落和有意义的小标题组织内容。一个段落只表达一个主要观点，避免堆叠多个无关结论。
- 第一次出现的业务术语、缩写或专有名词应给出全称或简要解释；后续保持用词一致。
- 代码块必须标明语言类型；命令、配置和代码示例应尽量保持可复制，必要时说明执行前提和预期结果。
- 链接文本应直接说明链接目标，避免使用“点击这里”等无法脱离上下文理解的文字。
- 表格用于表达结构化信息或对比关系，不在单元格中放置过长段落；复杂说明使用正文段落。
- 结论、待办事项和待决策事项应明确写出，不使用只有作者才能理解的省略表达。

## 方案文档规则

技术方案、架构设计、改造方案和实施计划等方案文档，必须明确说明以下信息。没有对应内容时，也应明确写出“无”，不能省略章节，让读者自行猜测范围。

### 现状

说明当前系统或业务的实际情况，包括已有行为、问题表现、影响范围和相关背景。涉及问题判断时，应尽量提供日志、数据、代码位置或其他可验证依据。

### 目标

说明方案要达成的结果，以及判断完成与否的标准。目标应描述可观察的业务或技术结果，必要时补充性能、稳定性、兼容性等指标。

### 非目标

明确本次方案不处理的事项、暂不改变的行为和不包含的范围。非目标用于防止实施过程中不断扩大范围，也用于帮助评审者准确判断方案是否满足本次需求。

### 约束

列出会影响方案选择和实施方式的限制条件，例如现有接口兼容性、数据结构、依赖版本、部署方式、权限要求、上线窗口、性能预算和团队资源。约束应区分已确认事实与待确认事项。

### 推荐结构

除上述必需章节外，方案文档通常应根据需要补充以下内容：

1. **方案概述**：说明选择该方案的主要原因和整体处理流程。
2. **详细设计**：说明模块边界、数据流、接口、状态变化和异常处理。
3. **实施步骤**：按可执行顺序列出代码、数据、配置和发布变更。
4. **风险与验证**：说明潜在风险、回滚方式、测试范围和上线后的观测指标。
5. **待决策事项**：列出需要评审或业务方确认的问题，不将未决事项伪装成已确定结论。
